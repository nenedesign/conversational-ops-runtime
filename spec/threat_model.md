# Threat Model

Scope: Phase 1, single-tenant, self-hosted deployment. The threat surface expands with multi-tenant SaaS; this document covers the current phase.

---

## Trust boundaries

```
External
  Client application (API key holder)
  Human reviewer (browser/approval console)
  Provider systems (payroll, booking, etc.)

Internal
  Agent API service
  Action Service
  Command Worker
  Database (Postgres)
  Message queue / outbox
```

External actors are untrusted. Internal services authenticate with each other via deployment-specific transport security (mTLS, signed tokens).

---

## Injection vectors

### Prompt injection via tool arguments

**Vector:** A malicious user message includes instructions that manipulate the model into constructing `arguments` for a tool call that misrepresent the intended action.

**Control:** The model's arguments are treated as untrusted input. The Action Service validates them against the tool contract schema (`spec/tool_contracts/`) before passing to `prepare`. The proposal content is generated by the adapter's `prepare` method, not copied from the model's arguments.

**Residual risk:** A sophisticated prompt injection that stays within valid schema values (e.g. changing `employee_id` to a target other than the one the user intended) will pass schema validation. Human review of the proposal content is the last line of defense.

### Request body tampering

**Vector:** Client supplies `tenant_id`, `approver_id`, or `proposal_version` in the request body to escalate privilege or manipulate approval records.

**Control:** `tenant_id` is always resolved from the API key, never from the request body. `approver_id` is always resolved from the API key identity, never from the request body. `proposal_version` on the approve endpoint is validated against the current approval state; supplying a stale version returns `409 stale_approval`.

### Replay attacks on webhooks

**Vector:** Attacker captures a valid webhook event and replays it to trigger a second processing.

**Control:** Webhook signature (HMAC-SHA256) includes the raw body. `X-Webhook-Timestamp` must be within 300 seconds of the current time. Receivers must deduplicate on `event.id` to handle legitimate at-least-once redelivery.

### Idempotency key collision

**Vector:** Client intentionally sends the same idempotency key with different parameters to force a different outcome to be recorded as the first call's result.

**Control:** The first-seen response is stored alongside the parameter hash. If the same key arrives with different parameters, `409 idempotency_conflict` is returned and the stored result is not affected.

### Stale approval exploitation

**Vector:** Approver reviews and approves a proposal based on resource state at time T. The underlying resource changes before the command is dispatched, making the approved action act on different data than the reviewer saw.

**Control:** `authorization.rechecked` compares the `resource_version` from the approved proposal version against the current provider resource version. If they differ, the approval is invalidated and a new proposal version is created. The reviewer must re-approve against the current state.

### Unbounded side-effect retry

**Vector:** Command worker retries a dispatched command indefinitely after an uncertain outcome, potentially committing the operation multiple times.

**Control:** The command `idempotency_key` is stable across all retry attempts. Providers that receive a duplicate key return `CommitResult(status="duplicate")`. The runtime does not automatically retry after a `command.unknown` event; reconciliation must complete first. Providers without idempotency support (Tier 1) are blocked from high-risk actions by default.

## Authorization boundaries

### Model authority

The model cannot authorize its own actions. The model's tool call is input to the `prepare` stage; authorization requires either a policy gate (`authorization.passed` without human review, for low-risk actions) or human approval. A model that outputs `{"tool_name": "...", "arguments": {...}}` has not created a command.

### Approval console authority

The approval console (browser) calls the same Agent API endpoints as any other client. It does not have a separate privileged path to the database or Action Service. An approval console that has been compromised can only perform actions permitted by the API key it holds.

### Command worker authority

The command worker reads commands from the outbox and calls provider adapters. It does not accept external input; it only processes records already in the database that were created through the governed lifecycle. A compromised command worker can replay previously authorized commands but cannot create new ones.

---

## Out of scope (Phase 1)

- Multi-tenant data isolation hardening (single tenant in Phase 1)
- Distributed rate limiting
- Secrets management (API keys stored in environment variables)
- Network segmentation between services
- Database encryption at rest
- Provider adapter sandboxing

These become in-scope before multi-tenant deployment.

---

## Logging and non-repudiation

All state transitions are recorded in `audit_events` as append-only rows. The `approver_id` on every approval decision is the identity resolved from the API key, not self-reported by the client. This supports non-repudiation: an approver cannot later deny that they approved a specific proposal version.

The `evidence_snapshots` table records resource state at the time of prepare. These are immutable (no-delete rule on the table). A human reviewer's approval is tied to the exact proposal version and the evidence that existed at that version. Both are preserved indefinitely.
